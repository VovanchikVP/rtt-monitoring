# RTT monitoring

Сервис следит за турнирами Российского теннисного тура: по id турнира сам
подтягивает карточку и состав участников с внешнего API, хранит историю
рейтинговых очков игроков и показывает актуальный список участников,
отсортированный по очкам.

## Как это работает

```
            ┌──────────┐   POST /tours    ┌───────────┐
  браузер ──┤ FastAPI  ├─────задача──────▶│ RabbitMQ  │
            │ + статика│                  └─────┬─────┘
            └────┬─────┘                        │
                 │                        ┌─────▼─────┐   HTTP   ┌──────────────┐
                 │                        │  celery   ├─────────▶│ API rtt      │
                 │                        │ worker    │          │ mytennis.online
                 │                        └─────┬─────┘          └──────────────┘
                 │                              │
              ┌──▼──────────────────────────────▼──┐      ┌──────────────┐
              │            PostgreSQL              │◀─────┤ celery beat  │
              └────────────────────────────────────┘      └──────────────┘
```

Эндпоинт только заводит запись турнира с одним полем `id` и ставит задачу в
очередь. Всё остальное — запрос к внешнему API, заполнение карточки, добор
игроков, связей и очков — делают фоновые задачи. Поэтому создание турнира
отвечает мгновенно и не зависит от доступности источника данных.

## Запуск локально

```bash
docker compose up -d --build
```

Поднимается всё сразу: PostgreSQL, RabbitMQ, API, worker и beat. Миграции
накатываются автоматически перед стартом API.

- интерфейс — http://localhost:8000
- документация API — http://localhost:8000/docs
- панель RabbitMQ — http://localhost:15672

Полезные переменные при запуске: `APP_PORT`, `APP_RABBITMQ_UI_PORT`,
`APP_FILL_TOURS_INTERVAL`.

### Без докера

Нужны запущенные PostgreSQL и RabbitMQ, параметры подключения — в `.env`
(за образец можно взять `.env.example`).

```bash
uv sync
uv run alembic upgrade head
uv run uvicorn app:app --reload
uv run celery -A src.celery.app:celery_app worker --loglevel=info
uv run celery -A src.celery.app:celery_app beat --loglevel=info
```

## API

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/tours` | список отслеживаемых турниров с числом участников |
| `POST` | `/tours` | добавить турнир по `id`, остальное заполнится само |
| `DELETE` | `/tours/{id}` | удалить турнир и его связи с игроками |
| `GET` | `/tours/{id}/players` | состав турнира, по убыванию очков |
| `GET` | `/players/{id}/points` | история рейтинга игрока, от старых записей к новым |
| `POST` | `/players/rating/refresh` | добрать историю рейтинга всех игроков за 12 месяцев |
| `GET` | `/health` | проба для healthcheck |

`POST /tours` принимает единственное поле и отвергает лишние:

```bash
curl -X POST localhost:8000/tours -H 'Content-Type: application/json' -d '{"id": 307095}'
```

Ответ `GET /tours/{id}/players`:

```json
[{"number": 1, "id": 100505, "name": "Иванова Анна Сергеевна",
  "age": 11, "city": "Хабаровск", "points": 510}]
```

`POST /players/rating/refresh` отвечает сразу (`202`) и ставит по задаче
на каждого игрока в базе:

```bash
curl -X POST localhost:8000/players/rating/refresh
# {"players": 42, "queued": 42, "months": 12}
```

Если брокер недоступен, ручка отвечает `503`: периодической задачи,
которая подхватила бы работу, на этот случай нет.

## Фоновые задачи

| Задача | Когда запускается | Что делает |
|---|---|---|
| `tours.fill_empty` | после `POST /tours` и каждые `FILL_TOURS_INTERVAL` секунд | находит турниры без данных, тянет карточку, добавляет игроков и связи |
| `points.fill` | раз в сутки в `FILL_POINTS_HOUR` | добирает очки игрокам, у которых нет записи за текущий месяц, и складывает их результаты по турнирам в `rating_details` |
| `tours.sync_players` | раз в сутки в `SYNC_TOURS_HOUR` | сверяет составы ещё не начавшихся турниров: добавляет недостающих, убирает лишние связи |
| `tours.search` | раз в сутки в `SEARCH_TOURS_HOUR` | ищет турниры по фильтрам из `search_settings` и ставит на отслеживание новые |
| `points.fill_history` | по `POST /players/rating/refresh` и на каждого нового игрока из `tours.fill_empty` и `tours.sync_players` | добирает историю рейтинга **одного** игрока за последние 12 месяцев, попутно наполняя `rating_details` |

Задачи идемпотентны: повторный запуск не создаёт дублей. Старые записи об
очках не удаляются — копится история, по одной записи на игрока в месяц.

### История рейтинга

`points.fill_history` принимает `player_id` и работает только по нему: смотрит,
за какие из последних 12 месяцев записей об очках нет, и запрашивает внешнее
API только по недостающим. Запись датируется первым числом месяца, поэтому
повторный запуск не делает ни одного запроса, а `points.fill` видит такой
месяц заполненным. Месяц, в котором игрока не было в рейтинг-листе,
записывается нулём — иначе он запрашивался бы снова и снова.

Паузы между запросами (`REQUEST_DELAY`, 2 секунды) выдерживаются на трёх
уровнях:

- внутри задачи — между запросами соседних месяцев;
- на входе в очередь — задачи ставятся с `countdown` 0, 2, 4, … секунд;
- на воркере — `rate_limit="30/m"`, то есть не чаще одного запуска в 2 секунды.

Строгие 2 секунды гарантированы внутри одной задачи; глобальный интервал
соблюдается, пока очередь разбирает один воркер — при нескольких процессах
запросы разных задач могут идти чаще.

## Интерфейс

`static/` — одна страница без сборки, отдаётся самим FastAPI: разметка в
`index.html`, стили в `styles.css`, логика в `app.js`.
Список турниров опрашивается каждые 3 секунды, **пока есть незаполненные
турниры**; как только все данные подтянуты, опрос прекращается. Состав
участников открывается по прямой ссылке вида `/#tour=307095`.

Завершённые турниры (дата окончания уже прошла) убраны под свёртку
«Завершённые турниры», свежие сверху; идущие и предстоящие остаются в
основном списке. Если выбранный турнир оказался в свёрнутой части, она
раскрывается сама.

Клик по игроку раскрывает под его строкой график изменения рейтинга
(повторный клик — скрывает). Игроки раскрываются независимо, открытых
графиков может быть сколько угодно. Высота графика — две высоты строки
игрока, она же пересчитывается при изменении размеров окна. График рисуется
инлайновым SVG без библиотек; у игрока без записей вместо него подпись
«рейтинг ещё не собран».

## Конфигурация

Все переменные читаются из окружения, локально — из `.env`;
полный список с примерами значений — в `.env.example`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `APP_DB_HOST` / `APP_DB_NAME` / `APP_DB_USER` / `APP_DB_PASSWORD` | — | подключение к PostgreSQL |
| `APP_RABBITMQ_HOST` | `localhost` | адрес брокера |
| `APP_RABBITMQ_PORT` | `5672` | порт брокера |
| `APP_RABBITMQ_USER` / `APP_RABBITMQ_PASSWORD` | `guest` | учётные данные брокера |
| `APP_RABBITMQ_VHOST` | `/` | виртуальный хост |
| `APP_FILL_TOURS_INTERVAL` | `300` | период поиска незаполненных турниров, секунды |
| `APP_FILL_POINTS_HOUR` | `3` | час UTC для обновления очков |
| `APP_SYNC_TOURS_HOUR` | `4` | час UTC для сверки составов |
| `APP_SEARCH_TOURS_HOUR` | `5` | час UTC для автоматического поиска турниров |

## Структура

```
app.py                      точка входа FastAPI, монтирование статики
src/api/routers/            эндпоинты: только сигнатуры и вызов сервиса
src/api/schemas/            схемы запросов и ответов
src/service/                бизнес-логика эндпоинтов
src/celery/app.py           инстанс celery, расписание beat
src/celery/tasks.py         определения задач
src/celery/service/         бизнес-логика задач, по файлу на задачу
src/models/                 модели SQLAlchemy
migration/                  миграции alembic
static/                     интерфейс: index.html, styles.css, app.js
ci/                         манифесты k3s, см. ci/README.md
```

Схема данных: `tours` — турниры, `players` — игроки, `tours_players` —
связь многие-ко-многим, `points` — история очков с уникальным ключом
`(players_id, date)`, `rating_details` — результат игрока в турнире (место
и начисленные очки) с уникальным ключом `(tour_id, player_id)`.

Ответ `rating.details` несёт не только очки игрока, но и список его турниров,
поэтому обе задачи по очкам заодно наполняют `rating_details`. Турнир, которого
ещё нет в `tours`, заводится по данным из этого же списка: название, город и
одна дата — она же начало и конец. Место бывает диапазоном вида `17-32`, поэтому
хранится строкой. Уже заполненную карточку турнира это не трогает.

### Тесты

`tests/` закрывают все три запроса приложения к внешнему API:

| Файл | Метод API | Где используется |
|---|---|---|
| `test_tour_card_main.py` | `tour.card.main` | заполнение турниров и сверка составов |
| `test_rating_details.py` | `rating.details` | обновление очков игроков |
| `test_tour_roster.py` | `tour.roster` | автоматический поиск турниров |
| `test_rating_history.py` | `rating.details` за прошлые месяцы | добор истории рейтинга игрока |

Ручки игроков закрыты отдельно: `test_player_points_endpoint.py` —
`GET /players/{id}/points` (порядок записей, пустая история, 404).
`test_rating_refresh_endpoint.py` — `POST /players/rating/refresh`:
одна задача на игрока, шаг `countdown`, пустая база и `503` при недоступном
брокере. Брокер подменяется, до RabbitMQ ничего не доходит.

Внешний API подменяется локальным сервером на aiohttp (`tests/conftest.py`),
то есть запрос уходит по-настоящему и проверяется то, что реально ушло в сеть:
поля формы, браузерные заголовки, разбор JSON, присланного с типом `text/html`,
и ошибка на ответ 4xx/5xx. Для `tour.roster` дополнительно проверяется обход
страниц и предохранитель `MAX_PAGES`. Ни база, ни брокер, ни сеть наружу
не нужны.

Новая миграция после правки моделей:

```bash
uv run alembic revision --autogenerate -m "описание"
uv run alembic upgrade head
```
